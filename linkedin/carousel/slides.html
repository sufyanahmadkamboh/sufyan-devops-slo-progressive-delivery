DevOps project · explained simply

I built a system that releases new software to a few users first, measures if it's healthy, and automatically rolls it back if it's not.

1 of 5 servers gets the new version, so only ~20% of users see it.

Every 30 seconds a computer checks two numbers for the new version only:

❌ How many requests fail?   ⏱️ How slow is it?

Healthy?
20% → 40% → 60% → 80% → 100%

Unhealthy?
Removed. Everyone back on the old version.

Why & when to use it

Use this when a bad release costs you

  • You release often: weekly, daily, many times a day
  • Real customers use the service: shops, payments, apps
  • Someone is on call and you want fewer 3 AM decisions
  • You want "is it healthy?" to be a number, not an opinion
  • You run on Kubernetes and already have (or want) metrics

Probably not needed when…

  • a tiny internal tool has almost no traffic to measure
  • you release twice a year and can test everything by hand
How a team uses it

Release as usual. The system decides.

1
Agree on a target (SLO)"99.5% of requests must succeed, 95% must be faster than 300 ms."
2
The app reports its numbersRequests, errors and speed, collected by Prometheus every 5 seconds.
3
Ship a new version with one commandhelm upgrade … --set image.tag=1.2.0
4
Argo Rollouts releases it step by stepChecking the numbers for the new version at every step.
5
Watch it live on the dashboardPromoted ✅ or rolled back ❌. Nobody had to wake up.
Architecture

How the pieces talk

GitHub Actions: tests every change: unit tests, security scan, and a full rehearsal on a test cluster
▼
Helm: installs the new version with one command
▼
Argo Rollouts: moves traffic 20% → 100% and makes the final call
▲ ▼  "Is the new version healthy?"
Prometheus: collects errors & speed from every server, labelled by version
▼
Grafana: shows it all on a live dashboard

Everything runs on Kubernetes; I tested it on kind (Kubernetes on my laptop, free).

Implementation · the decision rule

The new version must pass both checks

❌ Failed requests
≤ 7.2%
= 0.5% error budget × 14.4. The same line that would wake up the on-call engineer.
⏱️ Speed (95% of requests)
≤ 300 ms
Measured on the new version only, never mixed with the old one.
# checked every 30 s, for the NEW version only successCondition: result[0] <= 0.0720 failureLimit: 1 # 2 bad checks → undo consecutiveErrorLimit: 4 # can't measure? → undo

🔒 Safety first: if monitoring is broken or the new version gets no traffic, the release is not promoted. No proof = no promotion.
